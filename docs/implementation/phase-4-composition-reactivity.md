# Phase 4 — Runtime Composition Reactivity

## Objective

Composition itself should begin reacting to:

- profile
- cadence
- scene modulation
- density
- cinematic pressure

WITHOUT:

- changing layout structure
- generating layouts
- dynamic render trees

This phase is about:

### runtime-influenced cinematic composition

NOT:

### adaptive UI systems

---

## Core Goal

Transform composition from:

```txt
manually tuned spacing
```

into:

```txt
runtime-influenced cinematic pacing
```

---

## What Needs To Become Reactive

The runtime should subtly influence:

- section breathing
- cinematic spacing
- reveal grouping
- compositional cadence
- experiential density
- visual pacing pressure

NOT:

- actual layouts
- responsive systems
- component structure
- render trees

---

## Implementation Direction

Create a composition reactivity layer.

Possible file:

```txt
runtime/presentation/composition/reactivity.ts
```

OR:

```txt
resolveCompositionPacing()
```

The system should produce:

- breathing values
- spacing pressure
- reveal grouping cadence
- cinematic separation
- compositional pacing

based on:

```txt
profile
+ cadence
+ scene modulation
+ density
```

---

## Important Constraint

This system should:

### influence composition

NOT:

### control composition

Meaning:

- subtle spacing shifts
- subtle pacing shifts
- subtle breathing changes
- subtle cinematic pressure

NOT:

- adaptive layouts
- dynamic composition generation
- runtime layout orchestration

---

## Desired Behavioral Consequences

### immersive + spacious

Should feel:

- deeper
- slower
- more breathable
- more cinematic

through:

- expanded spacing
- increased reveal separation
- deeper pacing

---

### editorial + tight

Should feel:

- sharper
- cleaner
- restrained

through:

- compressed breathing
- tighter grouping
- cleaner cadence

---

## DO NOT

❌ Create adaptive layout systems  
❌ Create runtime-generated spacing maps  
❌ Create scene-specific layout components  
❌ Create dynamic render orchestration  
❌ Create “smart layout engines”  
❌ Create orchestration state machines  

---

## Runtime Ownership Audit

Audit the following boundaries carefully.

---

## Cadence

Cadence should remain:

```txt
experiential pacing infrastructure
```

NOT:

```txt
global runtime state
```

Watch carefully for cadence inflation.

Cadence currently owns:

- fade timing
- reveal timing
- stagger
- section delay
- atmospheric intensity
- cinematic pressure
- motion restraint

This is acceptable now.
But monitor carefully.

---

## SectionMotionProvider

This provider should remain:

```txt
lightweight experiential bridge
```

NOT:

```txt
universal runtime coordinator
```

Avoid:

- duplicated orchestration logic
- hidden cadence resolution
- scene ownership leakage

---

## ProjectPresentationRenderer

Audit this carefully.

It is becoming:

### orchestration gravity center

Clearly separate:

- runtime responsibility
- presentation responsibility
- composition responsibility
- orchestration coordination

WITHOUT:

- micro-abstractions
- architecture theater

### experiential identities

NOT:

### style folders

- pacing softness
- cinematic pressure
- atmospheric depth

- compositional pressure

WITHOUT:

### authored and intentional

## Composition Stabilization Goal

The architecture is transitioning from:

```txt
runtime orchestrates motion
```

into:

```txt
runtime orchestrates composition feeling
```

This is the most important transition so far.

Focus on stabilizing:

- breathing
- cinematic spacing
- reveal grouping
- compositional pacing
- experiential density

Ensure:

- orchestration remains centralized
- semantics remain meaningful
- runtime authority remains clear

### produce meaningful experiential consequence
