# Project Conventions

## Architectural Philosophy

This project follows:

### runtime-directed experiential orchestration

The architecture prioritizes:

- authored cinematic restraint
- semantic causality
- centralized orchestration
- compositional pacing
- experiential cohesion

The project intentionally avoids:

- adaptive UI systems
- orchestration sprawl
- semantic inflation
- hyper-reactive runtime behavior
- dynamic layout generation

---

## Core Development Principle

Every new abstraction MUST:

### produce meaningful experiential consequence

If a new system:

- does not visibly improve orchestration
- does not improve experiential cohesion
- does not clarify runtime authority

then:
DO NOT ADD IT.

Avoid:

### architecture theater

---

## Runtime Ownership Rules

## Components

Components are:

### experiential render surfaces

Components should:

- consume orchestration
- remain declarative
- remain compositional
- avoid runtime ownership

Components should NOT:

- resolve orchestration
- own cadence logic
- own scene logic
- hardcode experiential behavior
- duplicate runtime semantics

---

## Runtime

Runtime owns:

- cadence
- scene modulation
- experiential pacing
- atmospheric orchestration
- composition modulation

Runtime should remain:

### centralized and restrained

Avoid:

- orchestration duplication
- hidden orchestration resolution
- provider inflation

---

## Providers

Providers should remain:

### lightweight orchestration bridges

Providers should NOT become:

### orchestration god objects

Avoid:

- hidden orchestration state
- duplicated orchestration resolution
- provider stacking complexity

---

## Themes

Themes are:

### experiential identities

NOT:

### styling presets

Themes should influence:

- atmosphere
- cinematic pressure
- compositional feeling
- experiential tone

Themes should NOT:

- orchestrate runtime logic
- own behavioral systems
- become plugin architectures

---

## File Naming

## ComponentsNamingConvention

Use:

```txt
PascalCase.tsx
```

Examples:

```txt
FadeIn.tsx
HeroSection.tsx
MotionCadenceProvider.tsx
```

---

## Utilities / Runtime Helpers

Use:

```txt
camelCase.ts
```

Examples:

```txt
resolveCadence.ts
sceneModulation.ts
reactivity.ts
```

---

## Constants

Use:

```txt
UPPER_CASE.ts
```

ONLY for:

- static constants
- immutable configuration maps

Avoid overusing constants folders.

---

### Import Conventions

Prefer:

```ts
import { ui } from "@/theme";
```

Avoid:

```ts
../../../theme
```

Use:

### stable architectural boundaries

Avoid:

### fragile relative traversal

---

### Component Structure

Recommended order:

```txt
imports
types
constants
hooks
component
helpers
exports
```

Keep components:

- thin
- declarative
- orchestration-consumptive

---

### Styling Rules

Prefer:

- composition
- utility abstraction
- theme-driven styling
- runtime-aware tokens

Avoid:

- inline styles
- duplicated utility groups
- arbitrary spacing values
- hardcoded cinematic spacing

Spacing should increasingly emerge from:

### compositional orchestration

---

### Motion Rules

Prefer:

- cadence-driven motion
- runtime orchestration
- scene modulation
- shared motion primitives

Avoid:

- hardcoded durations
- isolated easing systems
- component-owned motion semantics
- duplicated motion orchestration

Motion should remain:

### runtime-directed

---

### Composition Rules

Composition should:

- remain authored
- remain restrained
- remain cinematic
- subtly react to runtime modulation

Composition should NOT:

- dynamically restructure layouts
- generate adaptive rendering systems
- become runtime-generated UI

The runtime should:

### influence composition

NOT:

### control composition

---

### Documentation Rules

When introducing a new system, document:

- purpose
- responsibilities
- boundaries
- orchestration ownership
- integration points
- experiential consequence

If the system does not have:

### clear experiential consequence

reconsider whether it should exist.

---

### Anti-Patterns

Avoid:

❌ Semantic inflation  
❌ Runtime gimmicks  
❌ Adaptive layout engines  
❌ Dynamic orchestration systems  
❌ Plugin architectures  
❌ Orchestration duplication  
❌ Hidden runtime ownership  
❌ Component-owned orchestration  
❌ Experiential state graphs  

---

### Final Principle

Protect:

### authored cinematic restraint

The project becomes stronger through:

- deeper orchestration meaning
- clearer runtime authority
- subtler experiential modulation

NOT:

- more systems
- more abstractions
- more runtime complexity
