# Motion System

## System Identity

The motion system is architected as:

### runtime-directed experiential pacing infrastructure

Motion exists to orchestrate:

- cinematic pacing
- compositional breathing
- experiential continuity
- environmental pressure
- atmospheric restraint

Motion is:

### structural

NOT:

### decorative

---

## Core Motion Philosophy

Motion should communicate:

- pacing
- weight
- restraint
- atmosphere
- compositional rhythm
- experiential continuity

Motion should reinforce:

- hierarchy
- focus
- progression
- environmental feeling
- cinematic cadence

The goal is:

### authored cinematic pacing

NOT:

### expressive animation systems

---

## Runtime Motion Authority

Motion behavior should emerge from:

```txt
profile
→ composition contract
→ cadence resolution
→ scene modulation
→ runtime providers
→ component behavior
```

Motion should remain:

### runtime-directed

NOT:

### component-authored

---

## Motion Categories

## Entrance Motion

Used for:

- reveal
- emergence
- progression
- cinematic introduction

Entrance motion should feel:

- deliberate
- restrained
- compositional

Avoid:

- excessive spectacle
- theatrical animation
- aggressive transitions

---

## Atmospheric Motion

Used for:

- environmental continuity
- ambient cinematic feeling
- subtle experiential depth
- compositional atmosphere

Atmospheric motion should remain:

### nearly invisible

The user should:

### feel it more than notice it

---

## Interactive Motion

Interactive motion should:

- reinforce continuity
- preserve pacing cohesion
- maintain restraint
- respect compositional rhythm

Avoid:

- exaggerated hover systems
- disconnected interaction timing
- UI gimmicks
- overly expressive transitions

---

## Runtime Composition Motion

Motion should increasingly influence:

- section breathing
- reveal grouping
- cinematic spacing
- compositional pacing
- experiential density

WITHOUT:

- controlling layouts
- dynamically restructuring composition
- generating runtime UI systems

The runtime should:

### influence composition

NOT:

### control composition

---

## Motion Constraints

Avoid:

❌ Hardcoded durations  
❌ Isolated easing systems  
❌ Component-owned motion semantics  
❌ Aggressive spring physics  
❌ Excessive bounce  
❌ Chaotic timing  
❌ Animation spectacle  
❌ Disconnected transitions  
❌ Runtime animation state machines  

Prefer:

✅ Cadence-driven motion  
✅ Runtime orchestration  
✅ Cinematic restraint  
✅ Experiential continuity  
✅ Atmosphere-aware pacing  
✅ Compositional rhythm  
✅ Motion cohesion  

---

## Motion Providers

Providers should remain:

### lightweight orchestration bridges

Providers should:

- expose cadence
- expose modulation
- coordinate orchestration

Providers should NOT:

- own animation systems
- resolve hidden orchestration
- become runtime controllers

---

## Motion Tokens

Motion values should increasingly emerge from:

### orchestration contracts

NOT:

### local component tuning

Examples:

- duration
- stagger
- reveal offset
- section delay
- compositional breathing

These should remain:

### runtime-reactive

---

## Anti-Patterns

Avoid:

❌ Adaptive motion engines  
❌ Runtime sequencing systems  
❌ Stateful transition memory  
❌ Behavioral animation graphs  
❌ Dynamic cinematic choreography  
❌ Motion middleware systems  
❌ Animation plugin architectures  
❌ Hyper-reactive interaction systems  

---

## Semantic Constraint

Every motion semantic MUST:

### produce meaningful experiential consequence

If a motion abstraction:

- does not improve pacing
- does not improve orchestration cohesion
- does not improve cinematic feeling

REMOVE IT.

Avoid:

### motion inflation

---

## Final Principle

The strongest quality of the motion system is:

### restrained cinematic orchestration

Motion should feel:

- intentional
- compositional
- atmospheric
- cohesive
- runtime-directed

WITHOUT becoming:

- expressive spectacle
- orchestration noise
- animation theater
